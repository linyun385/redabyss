# INBOX 10 · U 批：问题清单 + 可执行施工单

> 前置：01 批的 `docs/design/ui/00_inventory.md` 必须已完成。
> 本批两段：先出**问题清单**（全量），再挑 P0/P1 出**施工单**（可直接照着改）。

## 第一段：问题清单 → `docs/design/ui/01_issues.md`

从 01 批的「已知问题」里汇总，每条一行，六列：

| 列 | 说明 |
|---|---|
| ID | `UI-001` 起编 |
| 区域 | 01 批的 10 个区域之一 |
| 问题 | 一句话，**必须是能验的事实** |
| 证据 | 文件:行号（可多条） |
| 严重度 | P0 / P1 / P2，定义见下 |
| 修法方向 | 一句话，不展开 |

**严重度定义（严格按此判，不许升格）**：
- **P0**：玩家会**卡住 / 看不懂该做什么 / 操作不了**。例：某按钮在 1024 宽下被挤出视口、某状态没有视觉区分导致误操作、键盘不可达。
- **P1**：玩家会**困惑 / 多操作一次 / 误读**。例：同一语义两个颜色、数值更新滞后、悬停说明缺失。
- **P2**：纯观感或不一致。例：圆角不统一、间距不等、字重跳。

排序：P0 先，同级别按「影响界面数」降序。

## 第二段：施工单 → `docs/design/ui/02_buildsheets/`（每个 P0/P1 一份）

文件名 `<ID>_<短名>.md`。每份固定六段：

```
# UI-0xx 短名

## 现状
（引用行号 + 当前代码片段，逐字贴，不许转述）

## 问题
（为什么是问题，违反哪条规范：UI.md 六义 / 字号表 / z-index 表 / 对比度阈值）

## 改法
（给出**完整可粘**的最小 diff 片段：CSS 规则或 JS 函数体。
 不许写「优化一下」；必须能让人直接搜到 old 粘 new）

## 影响面
（这个改动会波及哪些界面/状态；哪些地方依赖了旧行为）

## 验收
（改完必须跑：node tools/check_web.js、check_contrast.js 等；
 以及在 1280×720 / 1920×1080 两档下该看到什么。视觉部分写「需设计机在浏览器确认」）

## 风险
（会不会动到 RAW 那一行 / 引擎副本 / 地图模块；有没有别的任务依赖它）
```

**硬要求**：
- 每份施工单的「改法」必须**只动 `web/index.html` 的样式块或指定函数**，不许改数据、不许改引擎逻辑。
- 如果某个问题必须改引擎才能修，**不写施工单**，改写成 `## 需要引擎改动` 并在清单里标 `需引擎`，等设计机处理。

## 硬规矩

- 不许改 `web/` `engine/` `cards/*.json`
- 施工单只是方案，**不执行**
- 完成追加 `TASK_DONE.md`
- 做完不停，直接进 03 批
