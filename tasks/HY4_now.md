## 四个任务（H1–H4，各自独立，可中断续跑）

每块产出一个文件，**做完一块就能交付一块**，不用等全部做完。

### H1 · 隐形状态实证

**问题**：游戏里有大量状态（buff / debuff / 层数规则 / 共振 / 注视），玩家到底能不能看见？

**做法**：
1. 在 `web/index.html` 里找出所有**状态写入点**：给 `status.*` 赋值、往 buff 数组 push、
   设 `C.buffs` / `S.buffs` 之类的地方。
2. 对每一个状态 key，查三处有没有它的踪迹：
   - 渲染函数里（拼 HTML 字符串的地方、`s.push(` 的地方）
   - CSS 类里（`.st-xxx`、`.buff-xxx` 之类）
   - 界面文案里（`name:` / `label:` 映射表）
3. 判定：**玩家能否在界面上看见这个状态**（能 / 只能靠日志 / 完全看不见）。

**输出** `docs/design/ui/h1_invisible_status.md`：

| 状态 key | 写入行号 | 有无 DOM 显示 | 显示位置（行号） | 有无 CSS 类 | 玩家可见性 |
|---|---|---|---|---|---|

最后一节写：**总共几个状态 / 几个看不见 / 看不见的那几个分别影响什么玩法**。

**验收方式（我这边会做）**：随机抽 5 个 key，grep 它在 `index.html` 里的所有出现位置，对表。

### H2 · 键盘可达性实证

**问题**：这个游戏能不能全程用键盘玩？哪些界面必须点鼠标？

**做法**：
1. 找出所有 `addEventListener('keydown'` / `'keyup'` / `onkeydown`（含内联在 HTML 里的）。
2. 每个监听：绑在哪个元素上、支持哪些键、在什么条件下生效（有没有 `if (screen === 'battle')` 这类守卫）。
3. 把所有界面列出来（开始页 / 地图 / 战斗 / 事件 / 商店 / 营火 / 奖励 / 结算 / 图鉴 / 设置），
   标每个界面**有没有键盘入口**。

**输出** `docs/design/ui/h2_keyboard.md`：

第一张表：监听清单

| 位置（行号） | 绑定目标 | 支持的键 | 生效条件 | 作用 |
|---|---|---|---|---|

第二张表：界面 × 键盘矩阵

| 界面 | 有无键盘操作 | 能做什么 | 不能做什么（必须鼠标） |
|---|---|---|---|

### H3 · 规格漂移对账

**问题**：`docs/UI.md` 里写的规范（字号阶梯、颜色语义、z-index 层级），代码里现在还一致吗？

**做法**：把 `docs/UI.md` 里所有**数值型规范**（字号 px/rem、颜色 hex、z-index 数字、间距）逐条抄出来，
回 `web/index.html` 找**现值**，比对。

**输出** `docs/design/ui/h3_spec_drift.md`：

| 规范项 | 文档声称 | 代码现值 | 代码行号 | 一致？ | 漂移说明 |
|---|---|---|---|---|---|

**只对数值**。文档里的定性描述（「偏暗」「层次不清」）跳过，那是判断不是规范。

### H4 · 交互态矩阵

**问题**：每个能点/能选的东西，五种状态（默认 / 悬停 / 按下 / 禁用 / 选中）在 CSS 里定义了几个？

**做法**：
1. 找出所有可交互元素：`<button>`、`.btn`、手牌、地图节点、事件选项、奖励卡、标签页……
2. 对每一类，查 CSS 里有没有对应选择器：`:hover`、`:active`、`:disabled` / `.disabled`、`.selected` / `.on` / `[aria-selected="true"]`。
3. 注意区分：**有类名但没样式**（JS 加了个 class，CSS 里根本没写）也算缺。

**输出** `docs/design/ui/h4_interaction_states.md`：

| 元素类 | 选择器 | 默认 | :hover | :active | 禁用 | 选中 | 缺哪几态 |
|---|---|---|---|---|---|---|---|
