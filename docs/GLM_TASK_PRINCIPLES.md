# 给 GLM 派活的原则（2026-11-03 夜班实测后定）

> 起因：2026-11-02 夜班 10 小时只花掉 1.35 亿 / 3 亿额度，产出不小但效率结构失衡。
> 用户定下的方向：**让 GLM 做需要判断的活，重复劳动交给脚本。**

## 一、先看清钱花在哪

实测（`~/.zcode/cli/agents/*/metadata.json` 的 `usage` 字段，可随时重算）：

| 项 | 数值 |
|---|---|
| 夜班总 token | 6,780 万（181 个子代理） |
| input 占比 | **97.3%** |
| output 占比 | **2.7%** |
| input 里 cacheRead | 92.3% |

单个子代理平均 37 万 token，其中真正写出来的不到 1.2 万。
**结论：它主要是在「反复读上下文」，不是在「产出」。**

复算命令（随时可跑）：

```powershell
python -c "import json,glob,collections; a=collections.defaultdict(int); [a.__setitem__('t',a['t']+json.load(open(p,encoding='utf-8',errors='replace')).get('usage',{}).get('totalTokens',0)) for p in glob.glob(r'C:\Users\Administrator\.zcode\cli\agents\*\*\metadata.json')]; print(a['t'])"
```

## 二、分工判据（一句话版）

**这个活需要「读图 / 读代码 / 做取舍」吗？**
需要 → 给 GLM。
不需要，只需要「逐条照规则套」→ 写脚本。

## 三、具体分工表

| 活的性质 | 给谁 | 为什么 |
|---|---|---|
| 看图判断（质检、可辨识度、构图审查） | **GLM** | 脚本算不出「这一坨红是铁还是泥」 |
| 读代码找实现（规则文本 vs 引擎对账） | **GLM** | 要理解语义，正则办不到 |
| 数值取舍（哪天卡该削 1 点攻击） | **GLM** | 需要权衡，不是查表 |
| 文案写作（图鉴、副标题、台词） | **GLM** | 需要品味 |
| 逐条套规则（合规扫描、字段对账、清单生成） | **脚本** | 规则可写成代码，写一遍跑一万条 |
| 批量统计（覆盖率、分布、雷同度） | **脚本** | 确定性计算，LLM 会数错 |
| 逐条格式转换（json → md 表格） | **脚本** | 纯机械 |
| 汇总数字（「不合格多少张」） | **脚本** | 这次就栽在人工数错：自述 78，实数 125 |

## 四、四条派活规则

1. **凡是「改代码」的任务书，写死「必须产生 diff」**，验收要求给出前后行号对比或 `git diff --stat`。
   否则它会交一份审计文档说「分析完毕，代码零改动」——2026-11-02 的 T250–T257 就是这样。
2. **汇总数字一律由脚本生成**，不许人工写。任务书里直接指定「数字从 `<script>` 的输出里抄」。
3. **任务书里内联要用的数据切片**，别让每个 agent 自己读 461 条全表。
   181 个 agent 各读一遍全表，就是那 97% 的 input。
4. **判断类任务可以给大**：宁可一个 agent 判 50 张图，也别切成 10 个 agent 各判 5 张——
   切成 10 个，规则和上下文要读 10 遍。

## 五、额度烧不满的解释（别再纠结）

3 亿额度 10 小时用掉 1.35 亿，不是它偷懒。原因是**派出去的活里判断占比太低**：
47 组质检的结构完全一样，每个 agent 干的都是「读同样的规则 + 看不同的图」。
要烧满要么派更多真判断（美术决策、数值平衡、文案取舍），要么接受烧不满。

**开第二个 ZCode 会话没用** —— 那是把同一批上下文喂第二遍，input 翻倍、产出不变。
