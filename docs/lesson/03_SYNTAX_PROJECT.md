# 03 · 语法课（二）：这个项目特有的七件事

> 基础语法（02 篇）之外，这个项目还有七个「读到就会卡住」的写法：闭包、无递归的生长算法、事件监听、DOM 操作、localStorage、JSON 数据驱动、种子伪随机。每个都给真实行号。看完你能回答「为什么同一个种子每次画出同一张地图」和「存档到底存在哪」。

## 1. 闭包：随机数发生器为什么返回函数

全项目的随机性都出自这一个函数（地图库一份 [index.html:3980]、引擎一份 [index.html:5401]，代码相同）：

```js
  function makeRng(seed) {
    let s = (seed === undefined ? Date.now() : seed) >>> 0;
    return function () {
      s = (s * 1664525 + 1013904223) >>> 0;
      return s / 4294967296;
    };
  }
```

（[index.html:5401]。）逐行读：`s` 是内部状态；`>>> 0` 把数字按无符号 32 位整数处理（超出范围的位被截掉，相当于自动「卷回」0 到 2³²）；返回的匿名函数每被调一次，就把 `s` 乘 1664525 加 1013904223 再截断，除以 2³² 得到一个 0 到 1 之间的数。

**关键问题是：为什么返回一个函数，而不是直接返回随机数？** 因为随机数的本质是「一串有先后顺序、后一个依赖前一个的数」——`s` 必须活过两次调用之间。如果 `makeRng` 直接 `return s / 4294967296`，每次调用都从同一种子算出同一个数，游戏里所有「随机」都会是同一个数。返回函数之后，`s` 被关在这个函数的「背包」里（这就是闭包：内层函数记住了定义它时的变量），`makeRng(seed)` 返回的不是数，是**一条从此往后只属于你的随机数序列**。

实际使用能看出这个设计的另一个意图：地图库和引擎**各造各的发生器**（`const rng = opts.rng || makeRng(opts.seed)`，[index.html:5424] 附近与 `newRun` 里）——两个序列互不干扰，战斗里抽牌洗牌再多也不会「用掉」地图的随机性。如果用全局的 `Math.random()`：不可复现（见第 7 节）、无序列隔离、测试没法重放。

## 2. 递归与自调用：`growDAG` 里没有递归

任务书让我找 `growDAG` 的递归。找了：**没有**。`growDAG`（[index.html:4543]）从第一行起就是一套纯迭代结构：先建槽位表 `var slots = {}`（[index.html:4549]）、按配额把待落类型排进队列（[index.html:4555] 起），然后用循环逐个落子、逐条连边。它内部最像递归的函数 `hasDownPotential`（[index.html:4673]）拆开看也只是两层 `for`：

```js
    function hasDownPotential(tx, ty) {
      // T74: 槽位检查提前短路（常见命中省 36 次查格）；fb 查注入度帽
      for (var dy2 = 1; dy2 <= k; dy2++) {
        var yy = ty + dy2;
        if (yy >= h) break;
        var tb2 = bandOfY(yy, h, br), rl2 = yy - (tb2 - 1) * br;
        if (slots[tb2][rl2] && slots[tb2][rl2].length) return true;
      }
```

（[index.html:4673]。）它问的是「这个位置往下 k 格内还有没有空槽位」，命中就 `return true` 提前收工——是**循环加短路**，不是函数调自己。整个地图库（3967-5359 行）我都过了一遍，没有任何函数调用自身。

为什么这么大的生成算法能不递归：地图的结构是「分层往下的槽位填充」，天然是一个队列问题——每带该出几个战斗/精英/商店在 `quotaOrder`（[index.html:4554]）里写死，落一个删一个，`totalRemaining` 归零即结束。递归适合「结构未知、层层展开」的问题（树、目录）；这里结构是事先规划好的表格，迭代更直白也更好调试（哪一带没填满，打印那一带的槽位表就行）。

## 3. 事件监听：点击从哪里进来

界面上有三种监听写法并存。第一种，**元素级绑定**，出牌按钮和敌人框都是这么接的：

```js
$('#btn-end').addEventListener('click', () => {
  if (!C || C.over) return;
  pending = null;
  const beforeTurn = C.turn;
  RedAbyss.endTurn(C);
```

（[index.html:6956]。）`$('#btn-end')` 是 `document.querySelector('#btn-end')` 的缩写（`$` 在 [index.html:6436] 定义），`addEventListener('click', ...)` 在按钮被点时执行回合结束。第二种，**document 级监听**，全局键盘（方向键选路、W 切换世界、数字键出手牌）都挂在 `document` 上（[index.html:6922] 的 `document.addEventListener('keydown', ...)`），一次绑定、整个页面生效。第三种，**指针事件**——手牌拖拽用的是 `pointerdown/pointermove/pointerup` 三件套（[index.html:7894]、[index.html:8049]），不用 `click` 的原因 01 篇讲过：拖拽需要跟踪中间过程。

同一个动作往往有多条监听并存（点敌人 [index.html:7830]、拖到敌人 [index.html:8028]、详情面板打出 [index.html:8100] 三条路都通向 `doPlay`）——这不是冗余，是「鼠标流」和「键盘流」各自完整。

## 4. DOM 操作：界面是怎么被改的

全项目的 DOM 增改走三条路。**造元素**用两行的箭头函数助手：

```js
const el = (tag, cls, txt) => {
  const d = document.createElement(tag);
  if (cls) d.className = cls;
  if (txt !== undefined) d.textContent = txt;
  return d;
};
```

（[index.html:6429]。）`el('div', 'ename', e.name)` 一句顶四行——这个助手被调用的次数以千计，是整个 UI 层的砖。**清空重画**用 `textContent = ''`：`render` 每次都把敌人区清空重建（[index.html:7788] `ea.textContent = '';`），因为敌人数量会变，逐个 diff 不如推倒重盖。**含 HTML 的内容**用 `innerHTML`，只在拼接可信内容时用（比如图标 [index.html:7795]、遗物徽章 [index.html:7772]）；而玩家不可信的文本一律走 `textContent`（它不解析标签，天然防注入）。

改样式不用 `style` 逐项写，而是**切换 class**：`box.classList.add('hitflash')` 配 130 毫秒后移除（[index.html:7840]），动画全在 CSS 里定义。JS 只负责「什么时候挂上/摘下这个 class」，动效本身不占 JS 一行——这是 JS 与 CSS 的正确分工。

## 5. localStorage：存档与「没有存档」的处理

浏览器给每个本地页面一个键值仓库（关浏览器也不丢），存取只有 `setItem`/`getItem` 两招，值只能是字符串。项目用它存三样东西：通关记录、一次性教学提示的已读标记、字体设置。最有代表性的是教学提示：

```js
function onceHint(key, msg) {
  let show = true;
  try {
    const k = 'redabyss_hint_' + key;
    if (localStorage.getItem(k)) show = false;
    else localStorage.setItem(k, '1');
  } catch (e) { /* 存不了就本次会话提示一次 */ }
  if (show) toast(msg, 3000);
  return show;
}
```

（[index.html:7609]。）「没有存档」的处理分两层：`getItem` 对不存在的键返回 `null`（假值），`if` 一过就走「没读过→提示并记账」的分支；更外层的 `try/catch` 管**浏览器不让存**的情况（隐私模式、文件协议下 localStorage 可能直接抛异常）——存不了就退化为「本次会话照常提示」，游戏不崩。开局读通关记录用的是同一套路：`try { cleared = localStorage.getItem('redabyss_cleared') === '1'; } catch (e) {}`（[index.html:6472]）——注意 `=== '1'`，因为仓库里只有字符串，数字和布尔都必须自己转。

## 6. JSON 数据驱动：卡为什么不写死在代码里

打开 [index.html:6391]，一整行 `const RAW = {...}` 装下了全部卡牌、敌人、事件、遗物、层定义——这是构建脚本把 `cards/*.json`、`enemies/all.json` 等文件原样拼进来的产物（所以改 json 要重新拼一次才进游戏，见 04 篇的加卡清单）。为什么不直接在代码里写死 266 张卡：

好处一，**数据与规则分离**。`playCard`（[index.html:5694]）六道门、`applyCardEffect`（[index.html:5807]）逐字段执行——引擎只认识 `damage`/`block`/`special` 这些**字段名**，不认识任何一张具体的卡。加一张「伤害 99」的牌不需要动引擎一行。好处二，**非程序员可改**。json 里没有语法陷阱，改 `"damage": 10` 为 12 不需要懂函数。好处三，验收脚本能机械核对（`check_design_refs.py` 直接读 json 对账 id）。

代价也说实情：其一，`RAW` 那一行 300 多 KB 不可读——它是产物，人类只读源 json；其二，引擎内联副本与 `engine/core.js` 双份同步（00 篇结尾讲过），数据注入也要跑脚本；其三，字段名的解释权在引擎手里——json 里写一个引擎不认识的字段，不报错、也不生效（`applySpecial` 的 default 分支会打一句「这个效果这一版还没做」，[index.html:5875] 附近）。

## 7. 伪随机与种子：为什么地图能复现

`makeRng` 的公式 `s = (s * 1664525 + 1013904223) >>> 0` 是一个线性同余发生器（LCG）：下一个数由上一个数**完全确定**。所以「随机」其实是「一串看起来乱、实则可重放的数」——这就是伪随机。种子相同，整条序列相同，于是：

- 地图：URL 加 `?mapseed=12345`，`initRun` 就用 12345 当种子（[index.html:8661]），`generate` 内部再把种子乘 1000003 加尝试次数得到每轮的独立种子（[index.html:5304]），同一张图每次都一样长出来；
- 战局：`startRun` 用 `(Math.random() * 2147483647) >>> 0` 造一个局种子（[index.html:6462]）传给 `newRun`，之后抽牌、洗牌、血量掷骰全走这条序列——记下种子就能重放整局。

`Math.random()` 没有种子、不可重放，所以它只出现在「造种子」这一处。整座随机大厦的地基是一颗可记录的整数——这也是 00 篇说「引擎可以 node 跑测试」的前提：测试固定种子，结果就能断言。

## 8. 闭包三连问：用项目里的三个现场把它钉死

**一问：闭包「闭」住了什么？** 答：定义那一刻能看到的变量。`makeRng`（[index.html:5401]）闭住的是 `s`；`$`（[index.html:6436]）没闭住任何东西（只用参数）；`startCardPointer`（[index.html:7966]）闭住的最多——`d`（那张卡的 DOM）、`card`、`i`（下标）、`startX/startY`、`baseTx/baseTy/baseRot`（扇形偏移）。闭包的体积就是这些被抓住的变量的总和，抓住谁取决于**函数体里读到了哪些外层名字**。

**二问：闭包什么时候「活」，什么时候「死」？** 活到没有任何人引用它。`flyCard` 克隆出的残影节点 320 毫秒后 `remove`（[index.html:7645]），它的 setTimeout 回调闭包随之可回收；而 `makeRng` 返回的函数被 `run.rng` 长期持有（[index.html:5424] 附近），所以那颗种子状态活一整局。**闭包的寿命由引用它的变量决定**——这是理解「为什么全局状态要小心」的入口：`run`、`C` 活着，它们背后的几十个闭包就都活着。

**三问：同一个变量被多个闭包抓住，读到的是谁？** 是**同一个**。最典型的现场是手牌循环：`C.hand.forEach((card, i) => {...})`（[index.html:7874]）里每张卡绑一个 `startCardPointer` 回调——`forEach` 的参数是每次迭代的**独立**绑定，所以第 3 张卡的回调闭住的是 `card` 第 3 次的值。假如项目当年用的是 `var i` 的 for 循环加普通函数回调，所有回调闭住的会是**同一个**循环变量、读到循环结束后的终值——「点哪张卡都是最后一张」的经典 bug。项目用 `forEach` 参数绑定天然躲开了它，这是第 3 节事件监听能安全工作的底层原因。

## 9. `growDAG` 的迭代骨架：五行伪代码看懂 460 行

第 2 节说 `growDAG`（[index.html:4543]）没有递归，这里把它的迭代骨架压缩成五行伪代码（行号对应真实代码段）：

    准备：格子表、槽位表 slots、配额队列（按带分组）   [index.html:4544]-[index.html:4560]
    循环：只要还有待落槽位 totalRemaining > 0
      ├→ 按优先级挑一个 (带, 行) 槽位                  [index.html:4570] 附近
      ├→ 找一个不挤的落点（位移集 disp、间距 D 约束）  [index.html:4571] 附近，检查用 [index.html:4673] hasDownPotential
      ├→ 落节点、连边（连不上就连向上一带最近点）      [index.html:4607] addNode / [index.html:4617] addEdge
      └→ 槽位消耗，进入下一轮
    收尾：把孤岛并进主结构、统计剩余错误               [index.html:4980] 附近

为什么写成迭代而不是递归还有一层工程原因：**失败要能局部重试**。`generate`（[index.html:5299]）的重试循环整轮重来，而 growDAG 内部的落点尝试是「这个位置不行就换下一个」的循环局部回退——递归结构做局部回退要靠栈展开，迭代结构直接 continue。性能差异在 8×N 的格子表上是数量级的。

顺带把「槽位表」这个词讲清：`slots[b][rowLocal]` 是「第 b 带、带内第 rowLocal 行还欠几个什么类型节点」的账本（[index.html:4549]-[index.html:4551] 的注释），配额来自 `DEFAULTS` 的每带统计（[index.html:4035]-[index.html:4042]）。生成器本质上是在**还账**：账本说这带欠 3 个战斗、1 个商店，它就往格子上落、落满为止——「随机地图」的随机只出现在落点和连线方式上，**账本是确定的**。这也是 T330/T323 能精确统计「每带节点类型数量」的原因。

## 11. DOM 十二式：这个项目改界面的全部手法

1. **查一个**：`$('#btn-end')`，`$` 是 querySelector 缩写（[index.html:6436]）。
2. **查一批**：`document.querySelectorAll('#enemy-area .enemy:not(.dead)')`（[index.html:8060]）——CSS 选择器直接当查询语言用。
3. **清空**：`box.textContent = ''`（[index.html:7788]）——最快的「推倒重来」。
4. **建元素**：`el(tag, cls, txt)`（[index.html:6429]）。
5. **挂载**：`appendChild`（[index.html:7869]）。
6. **安全写文本**：`textContent`（[index.html:6432]）。
7. **写结构**：`innerHTML`，只喂常量（[index.html:7795]）。
8. **切样式**：`classList.add/remove/toggle`（[index.html:7707]、[index.html:7790]）。
9. **写内联样式**：`fill.style.width = ... + '%'`（[index.html:7821]）——血条是少数必须内联的（数值连续变化，class 表达不了）。
10. **量位置**：`getBoundingClientRect()`（[index.html:8065]）——落点判定的几何来源。
11. **定时摘除**：`setTimeout(() => n.remove(), ...)`（[index.html:7664]）——飘字的自毁。
12. **克隆**：`cloneNode(true)`（[index.html:7637]）——飞出残影是手牌的副本。

十二式里没有一式是冷门的，组合起来却覆盖了整场战斗的界面。特别指出第 9 式的分界：**连续量走 style、离散量走 class**——血条宽度、拖拽位移是连续的；受击闪光、选中高亮是离散的。项目从未用 style 写过离散状态，也从未用 class 表达连续值，这个分界值得照抄。

## 12. localStorage 三用途逐个拆

**用途一：通关记录**。`markCleared`（[index.html:7501]）在胜利/回头时写入：`localStorage.setItem('redabyss_cleared', '1')`，另维护一个结局收集表 `redabyss_endings`（JSON.parse 存进、push、再 stringify 存回）。读端在两处：`startRun` 判断是否二周目（[index.html:6472]）、`showGameOver` 判断凝视是否够开黯星回响（[index.html:7463]）。**写端在 try/catch 里、读端也在**（[index.html:6472]）——两端都防着「存储不可用」。

**用途二：教学提示已读标记**。`onceHint`（[index.html:7609]）用 `redabyss_hint_` 前缀 + 功能名做键，存 `'1'`。它的聪明处是**键即账本**——不需要一个「已读列表」，键存在就是已读。代价是没法批量重置（想重看教学得手动清存储），对这个体量的功能是划算的。

**用途三：字体设置**。`#font-plus` 按钮（[index.html:8264]）调 `document.body.dataset.fs` 并持久化（[index.html:934] 的按钮本体）——同一套 try/catch 套路。

三个用途合起来给出 localStorage 的使用心法：**只存小而离散的标记，存取都包 try/catch，键名带命名空间前缀**。它是给「跨会话的一枚开关」用的，不是数据库——项目没有把任何牌局进度存进去，死亡即重来（这个设计本身在 D10 方向池里有讨论空间）。

## 13. JSON 数据驱动的深读：adaptCard 为什么存在

第 6 节讲了「为什么不写死」，这里补讲**边界在哪里**。json 与引擎之间隔着一层 `adaptCard`（[index.html:6396]），它做的三件事：深拷贝（[index.html:6397]）、字段归一（`value`/`v` 双写兼容，[index.html:6400]）、语义提升（`exhaust`/`retain` 从 special 数组提升成 effect 顶层标志，[index.html:6405]-[index.html:6406]）。这层兼容层的存在暴露了一个事实：**json 的字段约定在历史上变过**，引擎不想改旧卡数据，就在入口做一次翻译。

从这里能推出「数据驱动」的真实成本清单：① 字段约定要有文档（`docs/content/README.md` 的名词表就是干这个的）；② 约定变更要写兼容层或迁移脚本；③ 引擎要拒绝不认识的字段（`applySpecial` 的 default 红字，[index.html:5874] 附近）；④ 数据构建产物（RAW 行）与真源（json）要靠脚本同步（[tools/_t46_wire.js:9]）。四条都对上了，数据驱动才是资产；缺任何一条，它就变成「用文件写死的代码」。

## 14. 种子的完整链路图

把第 7 节展开成一条可验证的链：

    局种子：(Math.random() * 2147483647) >>> 0        [index.html:6462]
      └→ newRun(opts.seed) → makeRng(seed)             [index.html:5424] → [index.html:5401]
          └→ run.rng 这一个函数被传遍整场战斗
              ├→ startCombat 敌人血量掷骰               [index.html:5545] 附近
              ├→ buildStarterDeck（不随机，但共享 rng）  [index.html:5457]

    地图种子：URL ?mapseed= 或随机                        [index.html:8661]-[index.html:8663]

## 15. 你改这里会发生什么（三个真实修改点）

**修改点一：把 [index.html:8662] 的地图种子解析删掉，永远用 Math.random。**
会发生的连锁：`?mapseed=` 失效，测试与录像无法复现同一张图——开发侧最先崩（`tools/` 里的地图回归测试全靠固定种子），玩家侧无感。验证：带 `?mapseed=7` 开局两次，地图不再一致即改成功；恢复方法是把解析行贴回去。这个修改点的意义：**一个功能可以没有玩家价值，却有不可缺的工程价值**。

**修改点二：把 [index.html:7615] 的 `localStorage.setItem(k, '1')` 挪出 try/catch。**
会发生的连锁：隐私模式（存储被禁）下 getItem/setItem 抛异常不再被吞——`onceHint` 直接抛错，调用它的 `startCombatFlow`（[index.html:6897]）整段中断，战斗能开但新手提示之后的所有逻辑停摆。验证：浏览器开「禁止站点存储」再进战斗。这是「防御不是装饰」的最快实证。

**修改点三：把 [index.html:5404] 的常数 `1664525` 改成 `1664526`。**
会发生的连锁：LCG 换了一个参数，序列质量可能变差（周期变短或分布出条纹），但**没有任何测试会失败**——项目的所有行为断言都建立在「同种子同结果」上，改参数后同种子同结果依然成立。这就是伪随机的本质：参数改了，「可复现」这个性质不丢，「随机质量」悄悄变了。验证手段超出本项目工具链（需要序列统计），所以这一改属于「能改但无法就地验证」——知道边界在哪也是能力。

## 16. 事件监听的三个时序陷阱（项目里都有防）

**陷阱一：指针离开元素，move 就断。** 手牌拖拽把 move/up 监听同时挂到卡面 `d` 和 `window` 上（[index.html:8049]-[index.html:8055]），注释 [index.html:8052] 写明是「备用：指针捕获失败时也能继续拖」——真正的第一道防线是 [index.html:7971] 的 `setPointerCapture`（把后续指针事件锁定给这张卡）。双保险的代价是 onUp 里要成对解绑六个监听（[index.html:8000]-[index.html:8005]），漏解一个就是内存泄漏加幽灵拖拽。

**陷阱二：拖动中途元素被重画。** render 全量重建手牌（[index.html:7873]），如果拖拽途中谁调了 render，被拖的那张卡 DOM 会被销毁——项目靠**状态位**（`dragging`、`pending`）而不是 DOM 身份维持拖拽逻辑，且拖拽期间 render 不会被触发（doPlay 在拖拽结束后才调）。你若在 onMove 里加任何会 render 的调用，就会当场复现「拖到一半卡消失」。

**陷阱三：同一事件挂多个监听的触发顺序。** Escape 的 keydown 有两个来源（[index.html:6949] 关弹层、[index.html:6953] 取消 pending），同一按键依次都会执行。顺序敏感的逻辑不能依赖多监听的先后（规范不保证跨目标顺序），项目里这两处恰好互不依赖——读代码时凡是「多个监听共享一个状态位」的地方都要做一次这种独立性检查。

## 17. DOM 性能的实话：一行「强制重排」的把戏

[index.html:7711] 有一行初读完全没道理的代码：

```js
    void document.body.offsetWidth;
```

它的上一行是移除 `shake` class，下一行是加回来（[index.html:7709]-[index.html:7712]）。意图：让「受到伤害」的抖动动画能**连续触发**——同一个 class 删了又加，浏览器会认为样式没变而不重播动画；中间强制读一次布局（offsetWidth），逼浏览器立刻结算「class 已移除」这个状态，再加回时动画才重播。同款把戏还出现在 [index.html:7921]（抽牌堆数字脉冲）与 [index.html:7944]（卡牌抖动）。这行代码没有任何「功能」，纯粹是向浏览器的渲染流水线低头——不理解它的人会当垃圾代码删掉，然后「受击抖动只在第一次生效」。**读到不理解的代码先 grep 它的兄弟**：三处同样的把戏凑在一起，意图就自己浮出来了。

顺带把性能的实话讲全：这个项目的 render 全量重画、动画全靠 CSS transition、没有虚拟 DOM——在「手牌 ≤10 张、敌人 ≤3 只」的数据量下，这些选择全部成立。第 11 节的十二式加上本节的强制重排，就是它对 DOM 性能的全部投入，没有更多了。

## 18. json 的第二个消费者：node 侧工具

RAW（[index.html:6391]）是 json 的**页面侧**消费者；同一批 json 还有 **node 侧**消费者：`tools/sim.js`（模拟器，文件头 [tools/sim.js:9] 自带一份 `const RAW = {...}` 副本）、`tools/_t46_wire.js`（重建器，[tools/_t46_wire.js:9] 用正则定位 RAW 行替换）、以及两个验收脚本直接读 json 对账 id。三个消费者围着同一份真源，各自有不同的同步方式：模拟器靠手工同步副本（它的 RAW 不在本次交付的自动同步范围内）、重建器靠脚本、验收脚本实时读。

这条事实的推论：**改 json 后要跑的不只是 `_t46_wire.js`**——模拟器的副本会滞后，用它验证平衡会拿到旧数据。看任何工具的结论前，先看它读的是哪一份数据。这个「多消费者围一个真源」的结构是这个项目最大的工程债（引擎双份誊抄同理），理解了它，你就理解了为什么 TASK_DONE 与任务书里反复强调「改完跑重建」。

## 19. 可复现性的另一根支柱：不靠随机的确定性

种子只保证随机序列可复现，但一张地图能被完整复现还需要**非随机部分也确定**。项目里有三处这样的设计：

其一，绑定表优先。节点绑定敌人/事件时先查 `MAPGEN_BINDINGS`（[index.html:973] 起的表），查到就按表分配、查不到才用生成器兜底（`resolveBinding` [index.html:5024]，`bindingFallbacks` 计数 [index.html:5302]）——同一张图上「第 2 带的战斗是 enemy_d2_01」是表定死的。

其二，哈希选图。敌人素材从三张生态图里选一张，用的是**id 字符求和取模**（[index.html:7800]）——不是随机数，是 id 的确定性函数。同一个敌人永远同一张图，且零存储成本。

其三，地名查表。节点地名从 `ECO_PLACES` 按节点 id 哈希取用（[index.html:8350] 附近，注释写明「确定性，不走 RNG」）——**不给随机数发生器添负载**，随机序列的全部预算留给玩法（抽牌、落点、掉落）。

三处合起来是可复现性设计的完整一课：随机预算是稀缺资源，能确定性的都确定性，随机只花在玩家能感知的地方。这也解释了第 7 节「为什么两个发生器分开」——预算隔离。

## 23. 闭包的代价：泄漏会从哪进

闭包不是免费的。每个闭包把它抓住的变量整体保活——`startCardPointer` 的回调闭住一张卡的 DOM、坐标、扇形参数，六处监听解绑之前（[index.html:8000]）这些全部不能回收。项目的释放纪律是「成对解绑 + 定时自删」（flyCard 的 `setTimeout(() => g.remove(), 320)`，[index.html:7645]）。可能出泄漏的三个口子：① 解绑漏了一侧（window 侧的三个监听）；② setTimeout 的延时回调引用了大对象，延时段内不许回收；③ `animQueue`（[index.html:7668]）积压——`pumpAnim` 只在 `done()` 被调时出队，忘调 done 的回调会让队列只增不减。排查思路也在这三条里：泄漏=「引用链没断」，顺着「谁还抓着它」问三层就能定位。

## 24. 诚实话：为什么这个项目不用框架

React/Vue 一类框架解决的问题是「数据变化 → 界面自动跟随」。这个项目的界面跟随是手写的（`render` 全量重画 + `prev` 差分做动画，01 篇第 5 节），框架能替掉它。不上框架的三个真实理由，从代码里都能读出来：① **双击即玩**——框架要构建链（npm/打包），这个项目的设计约束是「拷走 game 目录就能玩」；② **数据量小**——每帧重画的 DOM 以百计，框架的优化优势无从发挥；③ **改动者不是程序员**（用户原话见任务书），框架的组件化抽象对这个人是负担，`el()` 助手加模板字符串不是。代价也要知道：手写跟随意味着每加一个界面元素都要记得进 `render` 补一段差分（[index.html:7751] 的协议横幅就是按这个流程加的）——框架替你做的正是这部分纪律。

## 27. 事件对象里常用的五个字段

监听回调拿到的 `ev`（或 `e2`）是浏览器给的事件对象，项目里反复用它的五个字段：

| 字段 | 含义 | 项目现场 |
|---|---|---|
| `ev.clientX / clientY` | 指针在视口里的坐标 | 拖拽起点与落点判定（[index.html:7968]、[index.html:8025]） |
| `ev.button` | 按下的是哪个键（0=左键） | 只认左键拖拽（[index.html:7967]） |
| `ev.key` | 键盘字符 | Escape 判断（[index.html:6950]）、数字键解析（[index.html:8290]） |
| `ev.target` | 事件实际落在哪个元素 | 遮罩点击判断（[index.html:6934]） |
| `ev.pointerId` | 指针的唯一 id | `setPointerCapture` 锁定用（[index.html:7971]） |

读事件代码的心法：**先看回调读了这个对象的哪些字段，就知道它想响应哪种细节**——读坐标的是拖拽、读 key 的是热键、读 target 的是委托。少一个字段少一种能力，全读全用反而说明职责不清。

## 28. 立即与惰性：`initRun` 为什么能「等一等」

第 14 节链路图里 `initRun`（[index.html:8660]）是地图的起点，但它**不是页面加载时执行的**——它是惰性的：第一次 `showMap` 被调用时才跑（守卫在 [index.html:8918]：`if (!st.region || st.runRef !== run) initRun();`）。惰性初始化的两个触发条件写得非常讲究：`st.region` 不存在（第一次）或 `st.runRef !== run`（重开一局——run 是新对象，引用不同）。

惰性化的收益是**初始化顺序解耦**：`startRun`（[index.html:6461]）不需要知道地图模块存不存在，它只管调 `showMap`；地图模块也不需要在页面加载时抢跑。对照立即初始化的例子——`CLASS_POOL`（[index.html:6420]）在脚本加载时就求值（卡池数据时刻可用）、`animQueue`（[index.html:7668]）声明即用。什么时候惰性、什么时候立即？判据是**依赖是否就绪**：CLASS_POOL 依赖的 RAW 在上一行已就绪，所以立即；initRun 依赖的 run 还没被 startRun 创建，所以必须等。你在读任何初始化代码时都问一遍「它依赖的东西就绪了吗」，顺序问题就再没悬念。

## 29. 全局状态账本：页面级变量一共几个

流程层的全局状态（[index.html:6437] 一行声明 + 若干后补）逐个点名：

| 变量 | 类型 | 生命周期 | 谁写谁读 |
|---|---|---|---|
| `run` | 一局的所有进度 | startRun 到 restart | 引擎与流程层全都在读写（[index.html:6437]） |
| `C` | 当前战斗容器 | startCombat 到战斗结束 | 战斗 UI 与引擎分界（01 篇第 2 节） |
| `pending` | 待选目标的卡下标 | 一次点选 | [index.html:7830] 读、[index.html:8102] 写 |
| `rewardQueue` | 奖励步骤队列 | 一场战斗结束到发完 | [index.html:7132] 组装、[index.html:7145] 消费 |
| `shopState` | 货架快照 | 一次进店 | [index.html:6820] 声明、[index.html:6833] 消费 |
| `phase` | 当前屏幕状态 | 整局 | showScreen 族切换（[index.html:6505]） |
| `prev` | 上一帧界面的快照 | 每帧被 render 覆盖 | 差分动画的对照面（[index.html:6888] 声明） |
| T56 的 `st` | 新地图模块的私有状态 | 模块 IIFE 内 | initRun 起全套（[index.html:8666]-[index.html:8670]） |

读这份账本的两个收获：其一，全局状态总数是个位数且各自职责单一——「全局变量是万恶之源」在这类单页游戏里要打个折扣，**真正的危险不是全局，是无主的全局**（谁都能写、没人负责）；其二，`run`/`C` 是「引擎数据的镜像入口」——它们其实只是对引擎容器对象的引用，真正的数据在引擎内部（[index.html:5694] 的参数 C 就是同一个对象）。理解了「全局变量是引用不是拷贝」，就明白为什么引擎改了状态前端立刻能看见：看的本来就是同一块内存。

## 30. 两个发生器的隔离实验（想通可复现就靠它）

做一个思想实验：假如 `startCombat` 里的洗牌直接用 `Math.random()` 而不是 `C.rng`（对照 [index.html:5570] 与 [index.html:5408]），会发生什么？局种子还在、地图也照旧，但**抽牌顺序每次不同**——因为 Math.random 不在种子序列里。可复现性是「全有或全无」的：链路上任何一个随机源漏网，整局的复现就破功。项目把这一点守死的办法是**物理隔离**：引擎所有随机都走 `C.rng` 这一个函数引用（搜 `C.rng` 与 `run.rng` 的引用密度即可验证），地图侧全部走 `MG` 内部的 rng（[index.html:5305] 的局部 `rng`）。两个世界只有一个交集点——`newRun` 创建时把局发生器交给战斗容器（[index.html:5424] 附近），之后互不越界。

这给出可复现工程的实操口诀：**先审计随机源（列出所有随机调用），再统一入口（全部走注入的发生器），最后隔离预算（玩法与表现各用各的）**。第 19 节讲的哈希选图，就是「表现侧退出随机预算」的实例。

## 32. 名字冲突的现役防御

全局名字空间是共享的，项目防撞车的手段有三个，都有实据：其一，**IIFE 包私有**——MAPGEN-LIB 与 T56 模块的全部内部函数都锁在 `(function () { ... })()` 里（[index.html:3952] 附近、[index.html:8303]），对外只暴露一个名字；其二，**前缀命名**——`window.__SFX_LOG` 双下划线表示「调试专用勿依赖」，`redabyss_` 前缀圈走 localStorage 的键；其三，**导出面收敛**——core.js 明确列出导出清单（[engine/core.js:999]-[engine/core.js:1021]），不在清单上的函数外面拿不到。

你将来往项目里加新全局时的三条规则顺着这三道防御来：能进 IIFE 的不进 window；进 window 的先查这张表确认没撞名；起名用「项目前缀 + 语义」双段式。全局名字是公共走廊，三条规则就是走廊礼仪。
