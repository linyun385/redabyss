## 三、那有没有真需要扩的？

逐个清点后只发现两类「可扩而不损」的候选，均属可选优化而非薄弱修复：

1. `master/03_ENGINE.md` 的死代码表可补一列「本夜复核结果」（resonanceLock 读点/frail 实证/anmin_mark 现状）——但那是**更新**不是扩写，且该表已有「待确认」位承载此事。
2. `HANDOFF.md`（35 行，2026-10-29）已是历史交接，后被 HANDOFF_NIGHT_* 系列取代——历史文档不回写（与 T415 的「只报告不改」一致）。

**结论：零篇需要为「达到 200 行」而扩写。**

## 四、如果未来真要做「扩写批次」

给执行者的三条判据（比行数更有用）：
- 一篇文档该不该扩，看它**有没有未兑现的引用**（正文提到 X 但没有 X 的细节）——没有就不扩。
- 看它**是不是单功能短文**（操作单/索引/拍板记录）——是就不扩。
- 真要扩，扩的是**判断层**（结论为什么成立、反例是什么），不是把表格改写成散文。
