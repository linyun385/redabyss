# 06 · 需要新引擎能力的东西

> 本批 24 张新卡（`cards_draft.json`）**全部**只用现有白名单 code 与既有字段，零新引擎依赖——这是刻意的：设计先在现有引擎上立住，扩容另算。
> 本文列的是「现有引擎做不了、但设计上值得有」的东西。每条给出：缺什么、最小挂点在哪（均已读引擎核实）、卡面怎么写。**本文件不设计实现**，引擎侧怎么做由维护者定。

---

## 一、新 special code 提案（按性价比排序）

### 1. `parts_gain`（value：直接得 N 零件）

- **为什么缺**：现在产零件只有两条路——`mech_grow`（绑「打牌」）和 `parts_from_discard`（绑「先 discard_hand」）。没有「纯资金卡」，「攒钱」这个动作只能寄生在别的动作上。
- **最小挂点**：switch（5966）加一个 case，`C.parts += V`，约一行；零件跨战斗已由 `run.parts` 承担（7119/7351 行），无需新存储。
- **卡面草稿（2 张，不入 cards_draft.json）**：
  - 「工时预支」skill common 矿 1费：零件 +3。flavor：「先把零件发给你。之后的三回合，你替它干活。」（后半句是文案，效果就一行）
  - 「库存分红」power rare 矿 2费：零件 +4，消耗。flavor：「分红按持股发。持股名单上只有它。」

### 2. `perm_max_hp`（value：永久最大生命 +N）

- **为什么缺**：支柱 A 的「永久成长」现在只有力量一条数值线。生命上限是矿脉最直觉的「变厚」，而引擎只实现了它的**负向**（vitality 代价扣 run.maxHp，6092 行），正向没有入口。
- **最小挂点**：run.maxHp 字段已存在且跨战斗有效，case 里 `C.run.maxHp += V; C.run.hp += V` 即可。
- **卡面草稿（1 张）**：「扩容批文」power uncommon 矿 1费+4零件：最大生命 +5（一局内）。flavor：「批准你的外壳扩建五格。扩建期间的住宿自理。」

### 3. `perm_energy`（value：每场战斗能量 +N）

- **为什么缺**：永久能量是支柱 A 最想要的第三条线，而它的存储字段**已经存在且已在被读**：`run.energyBonus`（5652 行 `C.energy = run.energyMax + (run.energyBonus||0) - ...`），全库 grep 只有这一处读、**零处写**。引擎侧几乎白捡。
- **最小挂点**：case 里 `C.run.energyBonus = (C.run.energyBonus||0) + V`。
- **卡面草稿（1 张）**：「供电增容」power rare 矿 1费+6零件：每场战斗能量上限 +1（一局内）。flavor：「增容申请写的是『设备用电』。设备指你。」

### 4. `start_block`（value：每场战斗开始获得 N 格挡）

- **为什么缺**：战斗初始化硬编码 `block: 0`（5530 行），没有开场钩子。「上一场的余劲带进下一场」做不了。
- **最小挂点**：需要新 run 字段（如 `run.startBlock`）+ 战斗初始化读它。这条是四条里动得最多的，优先级最低。
- **卡面草稿（1 张）**：「交接班记录」skill common 矿 1费：本场战斗结束时，你的格挡保留一半到下一场。flavor：「交接单最后一栏：留给下一班。」（注：这条还要「战斗结束时结算」钩子，比 start_block 本身更大，若嫌重可退化成「下一场战斗开始时获得 6 格挡」的纯正面版。）

## 二、anm_0052 子代理 · 重做需求（引擎侧负责，本文件只写需求与卡面）

- **现状**：已按「伪敌方」方案落地（`_VERIFY_anmin_core_cards.md` 第二节 2.2）：住在敌方列表里的己方单位，替玩家承伤、打真敌人、每回合 +5 血 +2 攻、扣 1 零件。
- **若要重做，需要的新能力**（现状做不到的）：
  1. 独立的**友方单位列表**——现在它混在敌方列表里，胜负判定、AOE 目标、威胁加成、死亡掉落都要靠 `!isMinion` 过滤逐处豁免（已豁免 6 处），再叠加任何第二种友军都会让过滤面继续扩大。
  2. 友军的**行动时序**——它现在借敌方行动回合出手；要有「我方回合末行动」就得动回合结构。
  3. 玩家对友军的**指令交互**——现在它自动选目标；任何「指定它打谁/挡谁」都需要新的选择交互（引擎目前没有「选一张/选一个目标」的通用交互，见 07 派单 2.3）。
- **卡面怎么写**（维持现状即可，只建议两处文案补丁）：
  - cost_text 建议从「零件 -5」扩成「零件 -5；它每回合吃 1 零件长大」——每回合扣 1 零件现在只出现在日志里，卡面看不见。
  - flavor 保持「它替你站着。你站着，看它站着。」

## 三、anm_0053 悬浮体 · 重做需求（引擎侧负责，本文件只写需求与卡面）

- **现状**：用「每回合发触发牌」绕开了引擎没有的「卡牌留场」（`floating_body` → `makeFloatingToken`，`_token` 牌不洗回牌库、战斗结束消失）。
- **若要重做（真正留场），需要的新能力**：
  1. **卡牌留场持续生效**本身（07 派单 2.3 明确没有）：留场物的存储位（挂在 C 上）、每回合触发钩子（beginTurn 已有，可复用）、战斗结束清理、**UI 的「场上区」**——当前界面没有地方放一个不在手里也不在敌方列表的东西，这是三条里最贵的一条。
  2. 多个悬浮体的**区分展示**——现在 5 个悬浮体只是「每回合多 5 张触发牌」，留场化之后 5 个个体要不要各自显示、各自被攻击，都要引擎侧先回答。
- **卡面怎么写**：保留 `no_bonus: true`（卡面写明「不受任何加成」）与 `part_cost`；若留场化，flavor「它没有在飞。它只是还没决定往哪边掉。」仍然成立，不用改。

## 四、引擎侧待确认问题（不是需求，是本批设计踩到的语义边界）

1. **`mech_grow` 是赋值不是累加**（6025 行 `C.buffs.mechGrow = V`）。0051·Ⅱ 的升级靠「追加条目后处理顺序在base之后」才生效；本批 0058/0060 与 0051·Ⅱ 同回合存在降速 case（矩阵见 `05_curves.md` 第二节）。要么 handler 改 `+=`，要么新增 `mech_grow_add`——引擎侧定，数据层无法表达。
2. **`upgrade.effect.special` 是追加语义**（6557 行注释：空数组才清空）。本批 24 张升级已全部避开「同 code 追加」，未来任何「升级把某 special 数值调大」的需求都会踩同一个坑。
3. **anm_0039 的 `v:4` 参数写法**：引擎兼容（6636 行读 `sp.v` 兜底），行为正确；建议规范化为 `value`，不急。
4. **cost_redirect 遗物会把非 lock 代价改写成凝视+2**（6074–6081 行）：本批 memory/lock 卡不受影响（0058-0081 无 memory/vitality/mark），只是提醒未来给黯民设计代价型卡时会和该遗物互动。

## 五、明确不要的东西（防跑偏）

- **不要第二种召唤物**——07 派单 2.3 的原话。子代理之外任何「场上单位」都先走第一节第 4 条之外的正路。
- **不要跨局（跨 run）持久化**——用户 01:15 已明确否掉 localStorage 元进度。`perm_*` 全部是「一局内」。
- **不要条件判定**（「若…则…」）——引擎是无条件线性执行。所有「想 if」的冲动，用汇率分层和代价类型表达。
